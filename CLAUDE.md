# CLAUDE.md — MicroDNS

## Project Overview

MicroDNS is a Rust workspace replacing PowerDNS + pdnsloadbalancer with a single binary: authoritative DNS, recursive DNS, load balancing, DHCP (v4/v6/SLAAC), and IPAM. Instance-per-network federated topology where each subnet runs its own instance.

## Architecture

- **Container runtime**: stormdbase (process supervisor, SSH, logging, health probes, busybox commands)
- **Database**: redb (embedded, ACID, memory-mapped — no external DB needed)
- **DNS**: hickory-dns 0.24 (auth + recursor)
- **HTTP**: axum 0.8 (REST API + dashboard)
- **gRPC**: tonic 0.12
- **Async**: tokio 1.x
- **Config**: TOML for bootstrap only, all runtime config stored in redb and managed via REST API
- **Messaging**: NATS (optional, for federation and event publishing)

## Build & Deploy

**Local machine is ARM64** (Apple Silicon Mac).

```bash
# One-step build + deploy (cross-compile, container build, push)
scripts/build-and-push.sh

# Manual steps:
cargo build --release --target aarch64-unknown-linux-musl
podman build --tls-verify=false --platform linux/arm64 -f Dockerfile.scratch -t registry.gt.lo:5000/microdns:edge .
podman push --tls-verify=false registry.gt.lo:5000/microdns:edge
```

- mkube auto-deploys — watches the registry, pulls new images (~2 min)
- Rust 1.88+ required (time-core needs edition2024)
- `.dockerignore` must have `target/` to avoid 4GB+ build context
- Base image: `registry.gt.lo:5000/stormdbase:latest` (not scratch)

## Key Design Decisions

### DNS NOERROR vs NXDOMAIN
When a name exists but has no records of the queried type (e.g., AAAA query for a name with only A records), microdns returns **NOERROR with empty answer**, not NXDOMAIN. This is critical because systemd-resolved does parallel A+AAAA lookups and NXDOMAIN on either poisons the entire result.

### DHCP Option 15/119 Handling
When `domain_search` (option 119) is configured on a pool, option 15 (domain name) is suppressed. Option 15 causes systemd-resolved to scope the DNS server to a single domain, breaking cross-network resolution.

### Database-Driven Config
All runtime config (pools, reservations, forwarders) is stored in redb and managed via REST API. TOML is only used for initial bootstrap. Changes take effect immediately — redb is memory-mapped, reads are free, no reload signals needed.

### DHCP Reservation Inheritance
Reservation fields are all `Option<T>`. When not set on the reservation, pool defaults are used. A minimal reservation only needs `mac`, `ip`, and `hostname`.

### Graceful Shutdown
API server has a 5s shutdown timeout, main binary has 8s overall timeout. Prevents container restart loops from long-lived WebSocket/SSE connections.

### Forward-with-Fallback
Each instance forwards queries for peer zones to the peer's DNS server. If the peer is down, serves a local copy of the zone data (non-authoritative, AA=0).

## Recent Fixes (2026-03-20)

- **NXDOMAIN → NOERROR**: Fixed parallel A+AAAA lookup poisoning for systemd-resolved
- **Option 15 suppression**: Prevents DNS scoping when domain_search is configured
- **Shutdown timeout**: 8s bounded shutdown prevents container restart loops
- **Cross-network forwarding**: All instances forward to all peer zones including reverse and utility zones
- **stormdbase migration**: Container base switched from scratch to stormdbase for process supervision, SSH, health probes

## Zone Transfer + NOTIFY (shipped in v0.6.0, API-managed in v0.7.0)

Primary announces, secondary mirrors — for the backup DNS server. Settings live
in redb behind `GET/PUT/DELETE /api/v1/zone-transfer/config` (`allow_transfer`,
`notify`, `secondary`) and are applied live; `[dns.auth]` seeds them on first
run only, because mkube regenerates the TOML. See `docs/zone-transfer.md`.

**Not yet pointed at anything.** The backup server it was built for still needs
identifying — do not use gt as the secondary. Deployed instances currently hold
only the seeded defaults: RFC1918 AXFR ACL, no notify targets, no mirrored
zones.

The hook that makes the primary side complete is `Db::increment_soa_serial` —
every writer ends a change there, so announcing from that one call covers the
API, DHCP, mDNS, Kubernetes and reverse-PTR sync without any of them knowing
NOTIFY exists. Anything new that changes zone data should keep calling it.

## mDNS Ingest (issue #8)

One shared zone, `mdns.lo`, held by a dedicated instance. Every other instance
listens on its own segment and registers what it hears into that zone over the
REST API, then points its own clients at the holder. A device keeps the address
it has on its own network; its name is simply `<host>.mdns.lo` everywhere.

Deployed topology:

- Network `mdns` — 192.168.12.0/24, `bridge-mdns`, DHCP off, created as an
  mkube Network CRD (which provisioned the bridge and the DNS pod).
- `dns.mdns.lo` (192.168.12.252) holds the zone (`holder` empty).
- gw, g8, g9, g10, g11, g16, g100 report into it (`holder: 192.168.12.252`).
  **gt is deliberately not part of this.**

Design notes worth keeping in mind:

- **No per-network subzones and no copies.** Both were tried and rejected:
  `mdns.g9.lo` put the device's location in its name; per-instance mirroring
  multiplied the zone and needed transfers between instances.
- **`RecordSource` decides ownership.** Records arrive as `source: mdns`, and
  each reporting instance persists the ids it created so it withdraws only its
  own names. Curated records in the zone are never touched.
- **Withdrawal waits out a 45 s startup grace.** An empty cache after a restart
  means nothing has announced yet, not that devices left.
- **Config lives in redb, not the TOML** (`PUT /api/v1/mdns/config`), because
  mkube regenerates `microdns.toml` from the Network CRD.

Full notes: `docs/mdns-ingest.md`.

## g16 on rose1 (verified 2026-09-04)

The g16 flat /20 (192.168.16.0/20, dsw1) is served by microdns, never by
RouterOS's own DHCP or DNS. On rose1 (192.168.1.1) that is:

- container `g16_dns_microdns`, root-dir `/raid1/images/g16_dns_microdns`,
  veth `veth_g16_dns_0` = 192.168.31.252/20 on `bridge-g16`, gateway .16.1
- `/ip/dhcp-relay` entry `relay-g16` on `bridge-g16` → 192.168.31.252;
  `/ip/dhcp-server` is empty on the whole router
- pool `g16-pool` is 192.168.30.1–.254 in the API (the reference TOML's
  16.100–30.254 range was narrowed in the running config); 19 reservations
- every peer forwards `g16.lo` and all sixteen `16-31.168.192.in-addr.arpa`
  zones to 192.168.31.252 (the reverse set was added live to gw/g8/g9/g100/mdns
  on 2026-09-04 — g10/g11/gt already had it)

### Reverse zones: one owner per /24

Every instance forwards every other network's `in-addr.arpa` zones to that
network's DNS (added live across all nine on 2026-09-04). This only works if
no instance hosts a *local* copy of a peer's reverse zone: hickory answers
from the local zone first, so a one-record `10.168.192.in-addr.arpa` on g8
turns every other g10 address into an authoritative NXDOMAIN there. PTR sync
(`reverse::serves_reverse_zone_v4`) therefore only creates or writes into a
reverse zone that already exists locally or whose address is inside a local
DHCP pool subnet. An instance with DHCP off (gt, g100, mdns) needs its own
reverse zone created once by hand, exactly as `scripts/bootstrap-gw252.sh`
does — after that PTRs flow into it as before.

Health: `curl http://192.168.31.252:8080/api/v1/health`. The reference config
is `config/deploy/microdns-g16.toml`; the running config is in redb.
